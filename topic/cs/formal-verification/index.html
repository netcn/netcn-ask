符号模型检测如何用二叉决策图（BDD）把指数级状态空间压缩到可处理规模？

How does symbolic model checking use binary decision diagrams (BDDs) to compress an exponential state space into a tractable one?

符号模型检测不逐个枚举状态，而是用 BDD 紧凑表示状态集合与迁移关系，通过关系映像（image computation）批量计算后继。BDD 的共享结构与化简能在许多实际系统中把指数规模压缩为多项式级表示。
Symbolic model checking does not enumerate states one by one; it represents sets of states and transitions compactly with BDDs and computes successors in bulk via image computation. The shared structure and reduction of BDDs compress exponential size to polynomial representation in many real systems.

CompCert 这类经过验证的编译器为什么能保证目标代码与源语义一致？

Why can a verified compiler like CompCert guarantee that target code matches source semantics?

CompCert 用 Coq 证明了每个编译阶段都保持程序语义（bisimulation），从而排除了传统编译器中由优化引入的错误。它是首个经机器验证、可用于安全关键系统的 C 编译器。
CompCert proves in Coq that each compilation phase preserves program semantics (bisimulation), ruling out errors introduced by optimizations that plague traditional compilers. It was the first machine-verified C compiler suitable for safety-critical systems.

分离逻辑引入分离合取,解决了霍尔逻辑处理堆程序时的哪个根本痛点?

Which fundamental obstacle of Hoare logic for heap-manipulating programs does separating conjunction remove?

经典霍尔逻辑论证修改堆的程序时必须显式写出帧公理,逐一声明所有未被触及的存储单元不受影响,规格随程序规模急剧膨胀。分离逻辑用分离合取 P*Q 断言两份资源同时成立且占用互不相交的内存,规格只需描述命令自己触碰的足迹,帧规则随后自动把结论推广到整个堆。Reynolds 在 2002 年的系统阐述让这一局部推理思想成为 Facebook Infer、VeriFast 等工业级指针分析工具的逻辑基础。
Reasoning about heap mutation under classic Hoare logic forces frame axioms enumerating every untouched memory cell, so specifications swell with program size. Separating conjunction P * Q asserts two resources hold simultaneously while occupying disjoint storage, letting a specification describe only the footprint a command touches, after which the frame rule lifts any proved triple to arbitrary extra heap for free. Since Reynolds formulated the discipline systematically in 2002, this local reasoning has underpinned industrial pointer-analysis tools such as Facebook Infer and VeriFast.

测试一万次没出错,和「数学上证明不出错」,差在哪一步?编译器自己也能被证明吗?

What separates ten thousand passed tests from a mathematical proof of correctness — can even a compiler be proven right?

测试只能证明bug存在,永远不能证明不存在:输入空间无限,抽样必有死角。形式化验证换路而行:把程序与规约译成逻辑公式,以定理证明器或模型检测穷尽所有行为,产出机器可检查的证明。里程碑是CompCert——勒鲁瓦用Coq证明C编译器从源码到汇编每一步变换都语义保持,现用于空客与轨交信号的认证工具链。代价同样真实:规约错则证明完美地错,人力成本高一个量级,故留给密码协议、飞行控制等失效代价最高的场景。
Testing shows bugs exist, never that they don't: input spaces are infinite and samples leave corners dark. Formal verification changes lanes — translate program and specification alike into logic, then exhaust all behaviors with theorem provers or model checkers, yielding machine-checked proofs. The milestone is CompCert: Leroy used Coq to prove semantic preservation for every pass of a realistic C compiler down to assembly, now inside certification toolchains for Airbus and metro signaling. The cost is honest too: a wrong specification yields perfectly wrong proofs, at an order-of-magnitude labor premium — so industry spends it where failure hurts most: crypto protocols, flight control, compilers.

有界模型检测（BMC）如何利用 SAT 求解器检查固定步数内是否出错？

How does bounded model checking (BMC) use a SAT solver to check for errors within a fixed number of steps?

BMC 把「在 k 步内是否存在违反性质的反例」编码为命题逻辑公式，交给 SAT 求解器判定。它能在有界深度内找到反例，但无法证明更深或全局的性质，需配合循环归纳。
BMC encodes the question of whether a counterexample violating the property exists within k steps as a propositional formula and hands it to a SAT solver. It can find counterexamples within the bound but cannot prove global properties beyond it without loop unwinding or induction.

交互式定理证明器（如 Coq、Isabelle）适合验证哪类性质，为什么需要人工参与？

What kinds of properties are interactive theorem provers (e.g. Coq, Isabelle) suited for, and why is human involvement needed?

它们用类型论或高阶逻辑表达证明，由用户一步步构造并交由机器检查，适合无法自动判定的深层数学与算法性质。人工参与在于提供证明策略与中间引理，机器只负责严格验证每步。
They express proofs in type theory or higher-order logic, with the user constructing steps that the machine checks, suited to deep mathematical or algorithmic properties that are not automatically decidable. Human input supplies proof strategies and intermediate lemmas; the machine only rigorously verifies each step.

形式化验证与传统的软件测试有何本质区别？

What is the essential difference between formal verification and traditional software testing?

测试通过抽样执行检查特定输入是否出错，无法穷尽所有情况；形式化验证用严格的数学逻辑证明程序满足规约，从而覆盖全部可能行为。代价是建模成本高，通常只对关键模块使用。
Testing samples specific inputs and cannot exhaust all cases, while formal verification uses rigorous mathematical logic to prove a program satisfies its specification, covering all possible behaviors. The cost is high modeling effort, so it is usually applied only to critical modules.

LTL 与 CTL 的表达能力为何互不包含?各举一个只能被其中一方表达的性质。

Why are LTL and CTL expressively incomparable? Give one property expressible only in each.

LTL 在单条执行路径上隐式量化,CTL 沿计算树的分支量化,公式结构不同导致二者互不包含。AFG(所有路径上最终恒成立)只能用 CTL 表达,FG(最终永远成立)只能用 LTL 表达;需要混合两种量词风格时必须诉诸 CTL*。
LTL quantifies implicitly over a single execution path while CTL quantifies over branches of the computation tree; their formula shapes differ, so neither subsumes the other. AFG — on every path, eventually always — is expressible only in CTL, whereas FG — eventually forever — only in LTL, and mixing both quantifier styles requires CTL*.

模型检测（model checking）是怎样自动判断有限状态系统是否满足时序性质的？

How does model checking automatically decide whether a finite-state system satisfies a temporal property?

模型检测把系统建模为状态迁移系统、把性质写成时态逻辑公式，再用穷举或符号搜索自动判定公式是否成立。它能在不满足时给出反例路径，但受状态空间大小限制。
Model checking models the system as a state-transition system and the property as a temporal logic formula, then uses exhaustive or symbolic search to decide satisfaction automatically. It can produce a counterexample path when the property fails, but is limited by state-space size.

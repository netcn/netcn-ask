缓冲区溢出（buffer overflow）为什么危险？有哪些缓解技术？

Why is a buffer overflow dangerous, and what mitigation techniques exist?

缓冲区溢出指程序向固定大小缓冲区写入超出其容量的数据，覆盖相邻内存，攻击者可借此篡改返回地址并执行任意代码，是早期多数蠕虫的根源。缓解手段包括地址空间布局随机化（ASLR）、数据执行保护（DEP/NX，使栈不可执行）与栈金丝雀（stack canary）等。这些技术由 NIST 与 CERT/CC 等机构长期推广。
A buffer overflow writes more data into a fixed-size buffer than it can hold, overwriting adjacent memory; attackers exploit this to hijack the return address and run arbitrary code, a root cause of many early worms. Mitigations include Address Space Layout Randomization (ASLR), Data Execution Prevention (DEP/NX, making the stack non-executable), and stack canaries. These techniques are long promoted by bodies such as NIST and CERT/CC.

AES 为什么能成为各国政府和企业广泛采用的对称加密标准？

Why did AES become the widely adopted symmetric encryption standard for governments and industry?

AES 是 NIST 在 2001 年通过公开竞赛选出的分组密码，以 Rijndael 算法为基础，支持 128/192/256 位密钥，既安全又适合硬件和软件高效实现。它取代了早期的 DES，成为数据加密的主流。
AES is the block cipher NIST chose through an open competition in 2001, based on the Rijndael algorithm, with 128/192/256-bit keys and efficient hardware and software implementations. It replaced the older DES as the mainstream data-encryption standard.

OAuth 2.0 的授权码模式为什么比把密码直接交给第三方应用更安全？

Why is the OAuth 2.0 authorization-code flow safer than handing passwords directly to third-party apps?

授权码模式下，第三方应用先把用户引导到授权服务器登录，用户授权后拿到的是"授权码"而不是令牌，并且令牌由第三方应用在后端用 client secret 换取，全程不经过浏览器。这样用户的密码不会泄露给第三方，令牌也减少了在浏览器中被截获的机会，还支持作用域限制和刷新令牌。
In the authorization-code flow, the third-party app redirects the user to the authorization server; after consent it receives an authorization code — not a token — and exchanges it for a token in the backend using its client secret, never through the browser. The user's password is never exposed to the third party, the risk of token interception in the browser drops, and scopes plus refresh tokens add further control.

最小权限原则（principle of least privilege）是什么？

What is the principle of least privilege?

最小权限原则要求每个程序与用户只拥有完成其任务所必需的最低权限，既不多也不少，从而限制一旦被攻破时的破坏范围。它由萨尔泽与施罗德在 1975 年的经典论文中系统提出，并被 NIST 采纳为安全设计的基本要求。它是纵深防御与权限隔离的理论基石。
The principle of least privilege requires that every program and user be given only the minimum permissions needed to perform its task, no more, limiting the blast radius if compromised. Systematized by Saltzer and Schroeder in their 1975 classic paper, it is adopted by NIST as a basic security-design requirement. It is the theoretical cornerstone of defense in depth and privilege separation.

Diffie-Hellman 密钥交换是怎样让双方在不安全信道上共享秘密的？

How does Diffie-Hellman key exchange let two parties share a secret over an insecure channel?

双方各自选私密指数，公开交换各自计算的幂值；由于离散对数难反解，窃听者拿不到中间结果也无法算出共同的共享密钥。Diffie 与 Hellman 在 1976 年发表，开启了无预先秘密也能协商密钥的可能。
Each side picks a secret exponent and publicly exchanges computed powers; because the discrete logarithm is hard to invert, an eavesdropper cannot derive the shared secret from what is visible. Diffie and Hellman published it in 1976, enabling key agreement without prior secrets.

跨站脚本（XSS）攻击是怎么发生的？

How does a cross-site scripting (XSS) attack work?

当网站把用户输入直接插进网页而不过滤时，攻击者提交的 <script> 代码会作为页面的一部分被其他用户的浏览器执行。这样能偷走别人的登录 Cookie、伪造表单或劫持会话。防御在于“输出编码”：把用户内容当纯文本渲染而非可执行代码，并配合 CSP（内容安全策略）限制脚本来源。
When a site inserts user input into pages without sanitizing it, <script> code submitted by an attacker executes in other users' browsers as part of the page. That lets attackers steal login cookies, forge forms, or hijack sessions. Defense is output encoding—rendering user content as inert text, not executable code—plus CSP (Content Security Policy) to restrict where scripts may come from.

TLS 是怎么在公开网络上保证通信既加密又不被篡改的？

How does TLS keep communication over public networks both encrypted and un-tampered?

TLS 先用非对称密码（如 RSA 或 Diffie-Hellman）完成身份认证并协商出对称会话密钥，之后用该密钥对流量加密并用消息认证码(MAC)检测篡改。握手还依赖可信证书链来验证对方身份。
TLS first uses asymmetric crypto (RSA or Diffie-Hellman) to authenticate and negotiate a symmetric session key, then encrypts traffic with it and uses a MAC to detect tampering. The handshake also relies on trusted certificate chains to verify identity.

RSA 公钥加密的安全性建立在什么数学难题上？

On what mathematical problem does RSA public-key encryption rely for security?

RSA 用一对公私钥，加密基于『大整数分解困难』：把两个大素数相乘很容易，但要从乘积反推这两个素数在经典计算机上极难。Rivest、Shamir 与 Adleman 在 1978 年提出，是现代公钥密码的奠基之一。
RSA uses a public/private key pair whose security rests on the hardness of factoring: multiplying two large primes is easy, but recovering them from the product is intractable classically. Rivest, Shamir, and Adleman proposed it in 1978, founding public-key cryptography.

什么是服务端请求伪造（SSRF）？为什么云环境中的攻击者格外关注链路本地地址 169.254.169.254 这样的实例元数据端点？列出几类有效的防御措施。

What is server-side request forgery (SSRF)? Why do attackers in cloud environments pay special attention to instance metadata endpoints such as the link-local address 169.254.169.254? List several effective defenses.

应用若不加限制地按用户提供的 URL 发起请求，攻击者便可驱使服务器访问其内网中本不该暴露的服务，这就是 SSRF。云实例的元数据端点绑定在链路本地地址上，仅实例内部可达，返回临时访问凭证等机密，被读取后攻击者即可冒充该实例提权。防御包括：域名白名单并在 DNS 解析后拒绝私网与链路本地 IP、禁止自动跟随重定向、为元数据服务启用须携带令牌头的会话（IMDSv2）、收紧出站网络策略。
When an application issues requests to URLs supplied by users without constraints, attackers can steer the server toward services in its own network that were never meant to be exposed; that is SSRF. A cloud instance's metadata endpoint binds to a link-local address reachable only from the instance itself, and it hands out secrets such as temporary access credentials, whose theft lets an attacker impersonate the instance. Defenses include domain allowlists with rejection of private and link-local IPs after DNS resolution, refusing automatic redirects, token-header sessions for metadata such as IMDSv2, and tightened outbound policy.

经典的缓冲区溢出攻击是怎么发生的？现代系统如何防御？

How does the classic buffer-overflow attack work, and how do modern systems defend against it?

如果程序向固定大小的栈缓冲区写入超长数据且不做边界检查，溢出数据会覆盖相邻的返回地址；攻击者把精心构造的地址与 shellcode 布局好，函数返回时 CPU 就跳到恶意代码执行。现代防御包括栈金丝雀（canary）、NX（禁止栈上执行）、ASLR 地址空间随机化、编译器加固选项，以及改用内存安全的语言。
If a program writes past the end of a fixed-size stack buffer without bounds checking, the overflow overwrites the adjacent return address; attackers lay out a crafted address and shellcode, and when the function returns the CPU jumps to the malicious code. Modern defenses include stack canaries, NX (no-execute stacks), ASLR address-space randomization, compiler hardening flags, and moving to memory-safe languages.

零知识证明让一方『证明知道某秘密』却不泄露秘密，这可能吗？

Can one party prove it knows a secret without revealing it—is zero-knowledge proof real?

零知识证明通过交互式挑战，让证明者以极高概率使验证者信服自己掌握某信息（如离散对数），却不让对方学到任何可用片段。Goldwasser、Micali 与 Rackoff 在 1985 年提出这一概念，如今用于隐私币和身份认证。
A zero-knowledge proof uses interactive challenges so the prover convinces the verifier it knows something (e.g., a discrete log) with overwhelming probability while revealing no usable information. Goldwasser, Micali, and Rackoff introduced it in 1985; it now underpins privacy coins and authentication.

为什么区块链难以篡改？

Why is blockchain hard to tamper?

每个区块头里写着前一个区块的哈希，改动任何一条历史交易都会让那一块的哈希变化，进而让它之后的所有块都指向错误的地址，整条链当场断裂。要真正改掉，攻击者必须把目标块之后的每个块都重新算一遍，并且算得比全网其余人更快，才能让自己的版本成为「最长链」被接受——在工作量证明下这就是拼算力，也就是常说的「过半算力」问题。再加上历史记录早已复制在成千上万台独立节点上，改自己那份没有意义。难篡改不是数学上的不可能，而是成本高于收益。
Every block header carries the hash of the block before it, so changing any past transaction changes that block's hash, which makes every later block point at the wrong address and the chain breaks. To really alter history an attacker must recompute every block after the target one and do it faster than the rest of the network combined, so that his version becomes the accepted longest chain - under proof of work that is a hash-rate contest, which is what the 'majority of hash power' phrase is about. On top of that, the history is already duplicated across thousands of independent nodes, so editing your own copy means nothing. Tamper-resistance is not mathematical impossibility; it is that the cost exceeds the payoff.

SQL 注入攻击是怎么回事，为什么参数化查询能防住它？

What is a SQL injection attack, and why does parameterized querying prevent it?

攻击者把恶意 SQL 片段拼进用户输入，使数据库误把其当作指令执行，从而窃取或破坏数据。参数化查询把代码与数据分开，转义并绑定变量，让输入永远只当数据、不当命令。OWASP 将其列为头号 Web 风险之一。
An attacker concatenates malicious SQL into user input so the database mistakes it for commands, stealing or wrecking data. Parameterized queries separate code from data by binding variables, so input is always treated as data, never as a command. OWASP lists it among top web risks.

浏览器与网站建立 HTTPS 连接时，TLS 握手大致做了什么？

Roughly what happens during the TLS handshake when a browser opens an HTTPS site?

TLS 握手在传输业务数据前完成三件事：协商密码套件（协议版本与加密算法）、用服务器证书验证服务器身份、通过密钥交换（如 ECDHE）在不暴露密钥的前提下生成共享的会话密钥。此后双方用对称密钥加密通信，保证机密性、完整性并具备身份认证。
Before any application data, the TLS handshake does three things: negotiate the cipher suite (protocol version and encryption algorithms), verify the server's identity using its certificate, and establish a shared session key via key exchange such as ECDHE without exposing the key. Both sides then encrypt traffic with symmetric keys, providing confidentiality, integrity and authentication.

数字签名怎么同时保证"内容没被改"和"确实是你签的"？

How does a digital signature prove both integrity and authenticity at the same time?

签名方对消息做哈希得到摘要，再用自己的私钥加密摘要形成签名；验证方用公钥解开签名恢复摘要，与对收到的消息重新计算的哈希比对。由于私钥只有签名者持有，能通过验证的签名必然出自持钥者；消息一旦被改动哈希就对不上，因此签名同时提供了完整性与不可抵赖性。
The signer hashes the message and encrypts the digest with their private key; the verifier decrypts the digest with the public key and compares it with a freshly computed hash of the received message. Because only the signer holds the private key, any signature that verifies must come from them, and any modification breaks the hash match — so signatures provide both integrity and non-repudiation.

密码学哈希函数为什么要求『抗原像』和『抗碰撞』？

Why must a cryptographic hash function be preimage-resistant and collision-resistant?

哈希把任意长度输入压成固定长度摘要，抗原像指无法从摘要反推原文，抗碰撞指难以找到两个不同输入产生同一摘要。这两者保证了数字签名、口令存储和完整性校验的安全基础（如 SHA 系列由 NIST 标准化）。
A hash compresses arbitrary input to a fixed digest; preimage resistance means you cannot invert the digest, and collision resistance means finding two inputs with the same digest is infeasible. Together they secure digital signatures, password storage, and integrity checks (e.g., the SHA family standardized by NIST).

Why is two-factor authentication (2FA) safer than a password alone? What counts as a "factor"?

Authentication factors fall into three types: something you know (password, PIN), something you have (SMS code, TOTP, hardware key), and something you are (fingerprint, face). 2FA requires two factors of different types, so even if attackers steal the password they cannot log in without the second factor — sharply reducing the impact of credential stuffing and phishing.

CSRF 攻击为什么不需要窃取密码，而是利用浏览器自动携带 Cookie 的机制？

Why does CSRF need no stolen password, exploiting instead how browsers attach cookies automatically?

登录后，会话 Cookie 由浏览器自动管理：向该站的请求都会自动附上它。恶意页面诱骗浏览器发出改邮箱、转账等变更请求时，Cookie 照常随行，服务器无从分辨用户本意与伪造——攻击者无需读取任何凭据。防御因此要补上意图证明：绑定会话的防伪令牌、限制跨站的 SameSite Cookie 以及 Origin 校验。
After login, a site's session cookie is managed automatically by the browser: every request toward that site carries it along. When a malicious third-party page tricks the browser into sending a state-changing request - changing an email address, transferring money - the cookie rides along as usual, and the server cannot tell user intent from forgery; the attacker never reads any credential. Defenses add explicit proof of intent: per-session anti-forgery tokens, SameSite cookies restricting cross-site sending, and Origin header checks.

零信任安全模型和传统的"内网可信"模型有什么不同？

How does the zero-trust security model differ from the traditional "trust the internal network" model?

传统模型假设内网可信、外网可疑，攻击者一旦进入内网就能低成本横向移动。零信任默认"永不信任、始终验证"：无论请求来自内网还是外网，都持续校验身份、设备健康与授权，并授予最小权限。它假设边界早已被攻破，把安全控制从网络层下沉到每个请求和资源。
The traditional model trusts the internal network and suspects the outside, letting attackers move laterally at low cost once inside. Zero trust assumes "never trust, always verify": every request, internal or external, is continuously checked for identity, device health and authorization, with least-privilege access. It assumes the perimeter is already breached and pushes security control down to each request and resource.

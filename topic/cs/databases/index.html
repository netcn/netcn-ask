什么是数据库范式（规范化）？

What is database normalization?

规范化通过把一张大表拆成多张结构合理的表并定义关联，来减少数据冗余和更新异常。常见范式从第一范式到第三范式逐级加强约束，BCNF 进一步消除函数依赖带来的异常。
Normalization splits one large table into well-structured ones with defined relationships to reduce redundancy and update anomalies. Common normal forms tighten constraints from 1NF through 3NF, and BCNF further removes anomalies from certain functional dependencies.

OLTP 和 OLAP 有什么区别？

What is the difference between OLTP and OLAP?

OLTP 面向日常交易，强调大量短小、实时的增删改查，如下单和扣款。OLAP 面向分析，处理大规模历史数据做聚合和报表，如销售趋势。两者在设计、索引和存储上差异很大。
OLTP serves daily transactions, emphasizing many short real-time inserts, updates, and queries like orders and payments. OLAP serves analysis, crunching large historical data for aggregation and reports like sales trends. Their design, indexing, and storage differ greatly.

SQL 注入攻击是怎么发生的？怎么防御？

How do SQL injection attacks work, and how are they prevented?

如果程序把用户输入直接拼进 SQL 语句，攻击者输入的引号和关键字就会改变语句语义，例如让“密码校验”恒为真或删除整张表。防御的核心是参数化查询：把输入当作数据而非可执行代码传给数据库。此外还要做输入校验、最小权限和错误信息脱敏。
When a program concatenates user input directly into SQL, an attacker's quotes and keywords change the statement's meaning—turning a password check always true or dropping whole tables. The core defense is parameterized queries, which pass input as data, not executable code. Input validation, least privilege, and sanitized error messages add further protection.

数据库事务的 ACID 分别指什么？

What do the ACID properties of a database transaction mean?

原子性要求事务要么全部执行要么全部回滚，失败即撤销；一致性保证事务前后数据始终满足约束；隔离性让并发事务互相看不到对方的中间状态；持久性确保提交后的修改在断电后依然保留。实现依靠预写日志（崩溃后重放恢复）、锁机制和可配置的隔离级别。这些保证是银行转账这类操作不出错的基础。
Atomicity requires a transaction to fully complete or fully roll back on failure; Consistency guarantees data obeys constraints before and after; Isolation keeps concurrent transactions from seeing each other's intermediate states; Durability preserves committed changes even across power loss. These rest on write-ahead logging (replay to recover after crashes), locking, and configurable isolation levels. Together they keep operations like bank transfers error-free.

数据库范式是什么意思？

What do database normal forms mean?

范式是设计关系表时减少数据冗余、避免更新异常的一组规则，从第一范式到第五范式逐级严格。例如第三范式要求非主键字段不依赖其他非主键字段。适度范式化可防止数据不一致，但过度范式化会降低查询性能。
Normal forms are rules for designing relational tables that reduce redundancy and avoid update anomalies, from first to fifth normal form, each stricter. For example, third normal form requires non-key attributes not to depend on other non-key attributes. Reasonable normalization prevents inconsistency but excessive normalization hurts query performance.

MVCC 是怎么做到读不阻塞写、写不阻塞读的？

How does MVCC let readers avoid blocking writers and writers avoid blocking readers?

多版本并发控制在更新时不覆盖原行，而是写入一个新版本并标记创建它和删除它的事务号，旧版本仍留在数据文件或回滚段中。每个事务启动时取一个快照（记录哪些事务号对它可见），读取时沿版本链挑出对该快照有效的那一版，于是读操作无需共享锁，也不会被并发写挡住。代价是死版本会堆积，需要 PostgreSQL 的 VACUUM 或 InnoDB 的 purge 线程清理，长事务会阻碍回收并放大表膨胀。
Under multi-version concurrency control an update never overwrites the row; it appends a new version tagged with the transaction ids that created and deleted it, while older versions remain in the heap or an undo area. Each transaction takes a snapshot of which transaction ids are visible to it and walks the version chain for the version valid under that snapshot, so reads need no shared locks and are never blocked by concurrent writes. The cost is accumulating dead versions, reclaimed by VACUUM in PostgreSQL and purge threads in InnoDB, and long-running transactions hold reclamation back and cause bloat.

What is database sharding?

分片是把一个大型数据库按某种规则（如用户 ID 取模）水平拆分成多个更小、独立的数据库实例，分布到不同服务器上。它能突破单机容量和性能上限，实现水平扩展。代价是跨分片查询和事务变得更复杂。
Sharding splits a large database horizontally by some rule, such as hashing the user ID, into smaller independent instances on different servers. It breaks through single-machine capacity and performance limits, enabling horizontal scaling. The cost is more complex cross-shard queries and transactions.

流处理中的"精确一次"（exactly-once）语义是怎么实现的？为什么难？

How is exactly-once semantics achieved in stream processing, and why is it hard?

精确一次要求每条事件对结果的影响恰好一次，即使节点崩溃重试也不重不漏。实现需要组合多种机制：屏障对齐的检查点（把算子状态与输入偏移一起快照）、故障后从最近的检查点重放、以及把输出以幂等或两阶段提交的方式写入外部系统。难点在端到端协调：重放时既要重新处理未提交的事件，又不能重复提交已经生效的结果。
Exactly-once requires each event to affect the result exactly once, with no duplicates or losses even when nodes crash and retry. Implementation combines several mechanisms: checkpointing with barrier alignment (snapshotting operator state together with input offsets), replaying from the latest checkpoint after a failure, and writing outputs idempotently or via two-phase commit to external sinks. The hard part is end-to-end coordination: replay must reprocess uncommitted events without double-committing results that already took effect.

数据库事务的 ACID 属性分别指什么？

What do the ACID properties of a database transaction mean?

ACID 指原子性（Atomicity，事务要么全做要么全不做）、一致性（Consistency，事务使数据库从一个合法状态变到另一个）、隔离性（Isolation，并发事务彼此不干扰）、持久性（Durability，一旦提交结果永久保存）。该术语由黑德与罗伊特在 1983 年系统总结，是可靠数据库系统的设计目标。实现上通常依赖日志、锁和崩溃恢复机制。
ACID stands for Atomicity (all-or-nothing execution), Consistency (a transaction moves the database from one valid state to another), Isolation (concurrent transactions do not interfere), and Durability (once committed, changes persist). The term was systematized by Haerder and Reuter in 1983 and is the design goal of reliable database systems. Implementation relies on logging, locking, and crash-recovery mechanisms.

The relational model is a mathematical framework introduced by Codd in 1970, built on set theory, so queries express logical conditions rather than manual traversal steps.

程序先用一条 SQL 查出 N 个主对象，随后在循环里为每个对象各发一条 SQL 去取关联数据，总共 1+N 次往返；单条查询都很快，但每条语句的网络与解析开销随 N 线性叠加，列表页因此明显变慢。解决办法是一次性批量取回关联数据，用 JOIN 或 IN (...) 做预加载，例如 Hibernate 的 join fetch、Django 的 select_related/prefetch_related、Rails 的 includes。诊断时打开 SQL 日志或看 APM 调用链，若单次请求的查询条数随列表条目数增长就该怀疑。
The code issues one query for N parent rows and then, inside a loop, one more query per row to load its association, giving 1+N round trips; each query is fast, but per-statement network and parsing cost grows linearly with N and list pages crawl. The fix is eager loading — fetch the children in a single JOIN or IN (...) batch, as with Hibernate join fetch, Django select_related/prefetch_related or Rails includes. To detect it, log SQL or inspect an APM trace and look for a request whose query count scales with the number of items displayed.

删掉大量数据之后，为什么数据库文件的体积并没有变小？

Why doesn't the database file shrink after you delete a large number of rows?

多数存储引擎的 DELETE 只把行标记为死亡并把所在页放回内部空闲列表，留给后续插入复用，并不把空间交还文件系统，这样可以避免昂贵的文件收缩与随后再次扩展。于是磁盘占用保持原状，只是内部出现空洞，PostgreSQL 里称为表膨胀。真正回收需要重写数据文件：PostgreSQL 的 VACUUM FULL 或 pg_repack、MySQL InnoDB 的 OPTIMIZE TABLE、SQLite 的 VACUUM，这些操作会加重锁或需要额外磁盘空间，通常安排在维护窗口执行。
In most engines DELETE only marks rows dead and returns their pages to an internal free list for reuse by later inserts, rather than handing space back to the filesystem, which avoids costly truncation followed by re-extension. So the file keeps its size while filling with holes — what PostgreSQL calls table bloat. Genuinely reclaiming it requires rewriting the data file with VACUUM FULL or pg_repack in PostgreSQL, OPTIMIZE TABLE for InnoDB, or VACUUM in SQLite, all of which take heavy locks or extra disk space and are therefore scheduled in maintenance windows.

数据库为什么要先写日志再改数据页（预写日志）？

Why do databases write a log record before modifying data pages (write-ahead logging)?

提交时把随机分布的数据页全部刷盘很慢，而把变更记录顺序追加到日志文件很快；只要日志已落盘，事务就可以宣布提交，数据页留待稍后惰性写回。崩溃恢复时按日志重做已提交但未写回的修改，并回滚未提交的修改，从而同时保证持久性与原子性。ARIES 协议进一步引入检查点和日志序列号，把恢复时需要扫描的范围限制在最近一个检查点之后，这套方案被现代引擎普遍采用。
Flushing scattered data pages at every commit is slow, whereas appending change records sequentially to a log is fast; once the log record is durable the transaction can report success and the pages can be written back lazily. After a crash, recovery replays committed changes that never reached the data files and rolls back uncommitted ones, delivering durability and atomicity together. The ARIES protocol adds checkpoints and log sequence numbers so recovery need only scan from the last checkpoint, and it underpins most modern engines.

Systems like Apache Flink offer event time, windowing and exactly-once semantics to handle disorder and replay.

Why does the write-ahead logging protocol insist that log records reach stable storage before the pages they describe, and what breaks when that order is reversed?

How can two transactions each pass snapshot isolation cleanly yet together violate an invariant the database never promised to protect?

快照隔离让每个事务读取一致的历史快照,而冲突检测只覆盖写-写冲突,读写依赖完全不在检查范围之内。值班医生的例子里,两人在各自快照中都看到值班人数不少于二,于是各自把本人设为休假并更新不同的行;任何一个事务单独串行执行都会留下一名值班医生,唯有并发交错才会让名单清空——引擎看不到任何写-写冲突,便放行了这两个本不该同时成立的提交。Berenson 等对 ANSI SQL 隔离级别定义的述评暴露了这类异常的模糊地带,后来的可串行化快照隔离通过跟踪危险的写读依赖环才把写偏斜纳入拒绝范围。
Snapshot isolation gives each transaction a consistent historical snapshot and detects only write-write conflicts, leaving read-write dependencies entirely unchecked. In the on-call doctors scenario, both read at least two doctors on duty from their snapshots and each sets herself off-call while updating her own row; either transaction serialized alone would still leave one doctor on duty, and only their concurrent interleaving empties the roster — yet the engine sees no conflict and commits both. Berenson et al.'s critique exposed such gaps in the ANSI SQL isolation definitions, and serializable snapshot isolation later closed them by tracking dangerous cycles of write-read dependencies.

银行转账扣了钱却没到账怎么办?事务的 ACID 是怎么兜底的?

Money left account A but never reached B — how do transaction ACID properties prevent this limbo?

转账被包进一个事务:减款与加款要么全成,要么全回滚,绝不停在中间——原子性。一致性靠约束(余额非负等)确保状态转移合法;隔离性靠锁或多版本并发控制(MVCC)屏蔽并发事务的半成品,杜绝脏读与丢失更新;持久性靠预写日志(WAL),改动先落日志再改数据页,崩溃后重放已提交、回滚未提交。于是只剩两种结局:整笔转账永久生效,或者什么都没发生。分布式场景把四性扩展到多机难度陡增,这正是共识协议存在的原因。
The transfer wraps in one transaction: debit and credit both succeed or both roll back — never stranded between (atomicity). Constraints such as non-negative balances keep the database legal (consistency); locking or MVCC isolates concurrent transactions so dirty reads and lost updates vanish (isolation); durability rides a write-ahead log — changes hit the log before data pages, and crash recovery redoes committed work while undoing stragglers. The feared scenario resolves to exactly two endings: fully applied forever, or nothing at all. Distributed databases stretch ACID across machines at steep difficulty — which is exactly why consensus protocols exist.
